# Stratum — 外の採掘器に仕事を配る

`oag-node run --stratum` で開く、採掘器向けの口の取り決めである。XMRig の
ような外の採掘器は、ここから仕事 (ブロックヘッダ) を受け取り、ナンスを
変えながら RandomX に通し、当たったら答えを返す。

**合意ルールの外の取り決めである。** ブロックの正しさは `SPEC.md` だけで
決まる。ここに書くのは、ノードと採掘器がどう話すかだけである。

---

## 1. 早見表

| 項目 | 値 |
| --- | --- |
| 通信 | TCP。改行で区切った JSON-RPC 2.0 (Monero の Stratum と同じ形) |
| ポート | mainnet **1919** / testnet 11919 / regtest 21919 |
| 既定の待ち受け | `127.0.0.1` (この機械の中だけ) |
| アルゴリズム名 | **`rx/oag`** |
| RandomX の設定 | **Monero の `rx/0` と同じ** (tevador/RandomX の既定の設定。v2 ではない) |
| RandomX の鍵 | 仕事の `seed_hash` の 32 バイトを**そのままの順で** |
| ハッシュする中身 | 仕事の `blob` (100 バイト) の**全体** |
| ナンスの位置 | **92 バイト目から 4 バイト、リトルエンディアン** |
| 当たりの判定 | ハッシュの**先頭 8 バイトをビッグエンディアン**で読み、`target` **以下**なら提出 |
| `target` の形 | 16 桁の 16 進 = 64 ビット整数をリトルエンディアンで並べたもの |

素の XMRig との違いは、太字の 3 点 (アルゴリズム名、ナンスの位置、当たりの
判定) だけである。

---

## 2. ヘッダ (blob) の並び

仕事の `blob` はブロックヘッダそのもの (100 バイト) である。PoW の入力は
ヘッダの符号化そのものなので (`SPEC.md` §9.1、§11.1)、採掘器はナンスを
書き込んで**全体を** RandomX に通す。

| バイト | 長さ | 中身 | 型 |
| ---: | ---: | --- | --- |
| 0 | 4 | version | u32 LE |
| 4 | 32 | prev_hash | 32 バイト |
| 36 | 32 | merkle_root | 32 バイト |
| 68 | 8 | timestamp | i64 LE |
| 76 | 8 | difficulty | u64 LE |
| 84 | 8 | height | u64 LE |
| 92 | 4 | **nonce の下位 32 ビット — 採掘器が書く** | u32 LE |
| 96 | 4 | nonce の上位 32 ビット — ノードが決める。**触らない** | u32 LE |

- ノードは 92〜95 バイト目を**必ず 0 で**送る。
- 96〜99 バイト目には、接続ごとに違う値が入っている。同じアドレスで何台
  つないでも、探す範囲が重ならない。
- 素の XMRig は 39 バイト目にナンスを書く。OAG ではそこはマークルルートの
  途中なので、書き換えると無効なブロックになる。

---

## 3. 当たりの判定

ブロックが有効になる条件は次のとおりである (`SPEC.md` §11.1)。

```
pow_hash をビッグエンディアンの 256 ビット整数として読む
pow_hash ≤ (2^256 − 1) / difficulty
```

仕事の `target` は、この右辺の**上位 64 ビット**である。

```
target64 = ((2^256 − 1) / difficulty) >> 192
```

採掘器は、1 回ハッシュするたびに次を確かめ、真なら提出する。

```
u64::from_be_bytes(hash[0..8]) <= target64
```

- 見るのは**先頭の 8 バイト**、読み方は**ビッグエンディアン**、比較は
  **以下 (≤)** である。素の XMRig は末尾の 8 バイトをリトルエンディアンで
  読み、未満 (<) で比べる。そのままでは当たりを見逃し、外れを出す。
- 上位 64 ビットだけで比べるので、ちょうど境目のハッシュは 256 ビットで
  比べると外れていることがある。それはノードが弾く。**当たりを取りこぼす
  ことは無い。**
- `target` の 16 桁は、`target64` をリトルエンディアンの 8 バイトに並べて
  16 進にしたものである。素の XMRig の読み方 (8 バイトなら LE の u64) の
  ままで正しく読める。
- 画面に出す難易度は `(2^64 − 1) / target64` で、ブロックの難易度とほぼ
  一致する。

ソロ (`--stratum` だけ) では、`target` は**ブロックの当たりそのもの**で
ある。当たるまで何も提出されない。プール (`--pool`) では、ブロックより
易しい「シェア」の `target` を配る (§8)。判定のしかたはどちらも同じで
ある。

---

## 4. シード

RandomX の鍵 (シード) は 2048 ブロックごとに変わる (`SPEC.md` §11.3)。
仕事ごとに `seed_hash` が付いてくるので、前の仕事と違えばデータセットを
作り直す。ノードは次のシードを前もって知らせない (`next_seed_hash` は
無い)。

`seed_hash` は、そのブロックのハッシュを 16 進にしたものである。
**バイトの順を入れ替えずに** 32 バイトに戻し、そのまま RandomX の鍵にする。

---

## 5. やり取り

1 行に 1 つの JSON を送る。行の長さは 16 KiB まで。

### 5.1 login (採掘器 → ノード)

```json
{"id":1,"jsonrpc":"2.0","method":"login","params":{
  "login":"oag1q…アドレス",
  "pass":"x",
  "agent":"XMRig-OAG/6.26.0",
  "algo":["rx/oag"]
}}
```

- `login` は**報酬を受け取る OAG アドレス**である。ノードのネットワークの
  アドレスでなければ断る。
- `アドレス.名前` の形で、機械ごとの名前を付けられる。`rigid` があれば
  そちらを名前に使う。名前はノードの記録に出るだけである。
- `algo` に `rx/oag` が無ければ断る。素の XMRig がつないできたときに、
  無効な計算を延々と続けさせないためである。`algo` が無ければ確かめない。
- ノードが同期の途中なら断る。追いついてからつなぎ直す。

応答:

```json
{"id":1,"jsonrpc":"2.0","error":null,"result":{
  "id":"00000001",
  "job":{ …§5.2 と同じ… },
  "extensions":["algo","keepalive"],
  "status":"OK"
}}
```

### 5.2 job (ノード → 採掘器、通知)

```json
{"jsonrpc":"2.0","method":"job","params":{
  "job_id":"3",
  "blob":"00000000dd55…(200 桁)",
  "target":"1e5260ae30100000",
  "algo":"rx/oag",
  "height":16965,
  "seed_hash":"7ddfebd8…(64 桁)"
}}
```

ノードは次のときに新しい仕事を送る。届いたら、前の仕事はやめて新しい
ほうを掘る。

- 先端が動いたとき (誰かがブロックを見つけたとき)。
- 先端が動かなくても 30 秒ごと (取引を詰め直し、時刻を新しくする)。

### 5.3 getjob (採掘器 → ノード)

```json
{"id":2,"jsonrpc":"2.0","method":"getjob","params":{"id":"00000001"}}
```

新しい仕事を組んで `result` に返す。形は §5.2 の `params` と同じである。

### 5.4 submit (採掘器 → ノード)

```json
{"id":3,"jsonrpc":"2.0","method":"submit","params":{
  "id":"00000001",
  "job_id":"3",
  "nonce":"bc060000",
  "result":"00000ce135fb…(64 桁)"
}}
```

- `nonce` は、92 バイト目に書いた 4 バイトを**そのままの順で** 16 進に
  したもの (8 桁) である。
- `result` は、そのナンスで計算したハッシュ (32 バイト) の 16 進である。

ノードは**申告されたハッシュを信じない**。自分で計算し直して突き合わせ、
難易度を満たすか確かめ、ブロックに仕上げてチェーンに渡す。

成功: `{"id":3,"jsonrpc":"2.0","error":null,"result":{"status":"OK"}}`

### 5.5 keepalived (採掘器 → ノード)

```json
{"id":4,"jsonrpc":"2.0","method":"keepalived","params":{"id":"00000001"}}
```

応答の `result` は `{"status":"KEEPALIVED"}`。10 分間何も来ない接続は切る。

### 5.6 誤り

誤りは `error` に入る。`{"code":-1,"message":"…"}` の形である。

| message (の始まり) | 意味 |
| --- | --- |
| `this node hands out rx/oag jobs only` | 採掘器が `rx/oag` を名乗っていない |
| `the login must be an OAG address` | `login` がこのネットワークのアドレスではない |
| `the node is still catching up` | ノードが同期の途中。あとでつなぎ直す |
| `log in first` | ログインの前に getjob や submit を送った |
| `unknown job` | その仕事はもう入れ替わった (直近 4 つまで受け付ける) |
| `duplicate share` | 同じ仕事の同じナンスを二度出した |
| **`the result does not match`** | **ノードが計算したハッシュと違う。** ナンスを書いた位置か、ハッシュした範囲が違う。ノードが計算した値が添えてある |
| **`low difficulty share`** | **難易度を満たしていない。** 当たりの判定 (§3) が違う |
| `stale` | 正しい当たりだったが、別のブロックが先に先端を伸ばした |

`does not match` と `low difficulty` が合わせて 16 回になった接続は切る。
答えを確かめるたびに RandomX を 1 回まわすので、でたらめな提出でノードの
手を塞がせない。

## 6. 検算用の値

本番のブロック 1 と 16965 である。この `blob` と `seed_hash` を RandomX に
通して `pow_hash` が出れば、ナンスの位置もハッシュの範囲も合っている。
ノードの試験
(`crates/oag-node/tests/stratum.rs::the_test_vectors_in_the_spec_are_real_mainnet_blocks`)
が、これらの値が本物であることを確かめ続けている。

```

```

           bbae524eacd6500682f58c38c653bd5526a52622927fd722bb80d25e9e42f743

## 7. 使い方

```sh
# ノード (同じ機械で掘るなら既定のままでよい)
oag-node run --network mainnet --stratum

# 同じ LAN の別の機械から掘らせるなら
oag-node run --network mainnet --stratum 0.0.0.0:1919
```

採掘器 (OAG 用の XMRig) には、`-o 127.0.0.1:1919 -u <自分の OAG アドレス>
-a rx/oag` のように渡す。

`0.0.0.0` で開くと、**届く人は誰でもこのノードで掘れる** (報酬はその人が
ログインしたアドレスに入る)。インターネットには開けないこと。

---

## 8. プール (`--pool`)

`--stratum` に `--pool` を足すと、ノードがプールとして動く。**採掘器の
側は何も変わらない。** やり取りも仕事の形も §1〜§6 のままで、違うのは
ノードが配る `target` と、報酬の流れだけである。

```sh
oag-node run --network mainnet --stratum 0.0.0.0:1919 --pool \
    --pool-fee 1 --pool-fee-address <運営のアドレス> --pool-min-payout 1
```

| | すること |
| --- | --- |
| `--pool` | プールとして動く。`--stratum` が要る |
| `--pool-fee <percent>` | 運営の取り分。既定 0。小数 2 桁まで |
| `--pool-fee-address <address>` | 取り分の受取先。取り分が 0 でなければ**必須** |
| `--pool-min-payout <OAG>` | これだけたまったら払う。既定 1 OAG |

### 8.1 報酬の流れ

1. ブロックの報酬の受取先は、採掘器のアドレスではなく**プールの鍵**に
   なる。鍵はノードが初回に作り、`<datadir>/pool.key` に置く。
2. 採掘器はシェアを出す。ノードはシェアごとにハッシュを計算し直して
   確かめ、ログインしたアドレスの名で数える。
3. ブロックが見つかったら、その時点の直近のシェアで報酬を分ける (§8.2)。
4. コインベースが成熟したら (120 ブロック後)、分け前を残高に移す。
   その間にブロックがチェーンから外れていれば、その分け前は消える。
5. 残高が `--pool-min-payout` 以上の人に、10 分ごとに 1 本の取引で払う。
   送金手数料は受取額から額に比例して引く。
6. 運営の取り分も同じ流れで `--pool-fee-address` に払う。

台帳は `<datadir>/pool.json` にある。払えるまでの間、**採掘者の取り分は
プールの鍵の下にある。** `pool.key` と `pool.json` を失えば払えなくなる。
運営する人は両方を控えておくこと。`pool.key` は `oag-wallet` では開けない
生の鍵である。

### 8.2 分け方 (PPLNS)

新しい順にシェアの難易度を足していき、合計が**ブロックの難易度の 2 倍**に
届くまでのシェアで、報酬 (運営の取り分を引いた残り) を難易度の比で分ける。
最後の 1 本は、はみ出した分を削って数える。割り切れない端数は運営に回る。

ブロックを見つけた人だけが得をしないように、また、儲かりそうなときだけ
来て帰る「プール渡り」を割に合わなくするためである。

シェアの記録はメモリにある。**ノードを再起動すると空になる。** 再起動の
直後に見つかったブロックは、再起動の後のシェアだけで分ける。

### 8.3 シェアの難易度

採掘器ごとに自動で合わせる。最初はブロックの難易度の 100 分の 1 から
始め、シェアが 6 本届くか 2 分経つたびに、**15 秒に 1 本**になるよう
見直す。1 回に動かすのは 4 倍までで、ブロックの難易度は超えない。変えた
ときは、すぐに新しい `target` の仕事を送る。

シェアがブロックの難易度も満たしていれば、それはブロックの当たりでもある。
ノードはそのままブロックに仕上げて流す。間に合わずに別のブロックが先に
来ても、シェアとしては数える (`status` は `OK`)。

### 8.4 支払いが承認されないとき

- 支払いの取引が mempool にある間は待つ。
- 取引の入力が使われていれば、承認されたとみなす。
- どちらでもないまま 10 ブロック経てば、同じ取引を出し直す。出し直せな
  ければ、**その額を残高に戻す**。払っていないものを払ったことにはしない。
- 承認を待っている支払いの入力は、次の支払いには使わない。
